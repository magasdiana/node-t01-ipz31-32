## BUG-005: `GET /reports/profit` — розбіжність між деталізацією витрат і `totalExpenses`

- **Endpoint:** `GET /reports/profit?month=2026-11`
- **Severity:** Medium (може впливати на фінансову звітність).
- **Статус:** CONFIRMED QA FINDING за отриманою Postman-відповіддю від 02.11.2026.

### Фактичні дані загального звіту

| Поле                    | Значення |
| ----------------------- | -------: |
| `expenses.rooms`        |   200000 |
| `expenses.salaries`     |  1000000 |
| `expenses.allowances`   |        0 |
| `expenses.meals`        |     9900 |
| Сума компонентів витрат |  1209900 |
| `totalExpenses`         |  1200000 |
| Різниця                 |     9900 |
| `revenue`               |    25900 |
| `profit`                | -1174100 |

Арифметична перевірка:

- Сума компонентів `expenses`: 200000 + 1000000 + 0 + 9900 = **1209900**.
- API повертає `totalExpenses = 1200000`, тобто на **9900 менше**.
- `revenue - totalExpenses = 25900 - 1200000 = -1174100`, отже `profit` узгоджується з підсумком `totalExpenses`, але сам підсумок не узгоджується з деталізацією.

### Фактичні дані групи 27 — E2E Test Group

| Поле                    | Значення |
| ----------------------- | -------: |
| `expenses.rooms`        |        0 |
| `expenses.salaries`     |        0 |
| `expenses.allowances`   |        0 |
| `expenses.meals`        |     9900 |
| Сума компонентів витрат |     9900 |
| `totalExpenses`         |        0 |
| `revenue`               |    25900 |
| `profit`                |    25900 |

Для групи 27 `expenses.meals=9900`, але `totalExpenses=0`; значення `profit=25900` відповідає `revenue - totalExpenses`, а не `revenue - сумі деталізованих витрат`.

- **Очікувано:** `totalExpenses` має узгоджуватися з деталізованими компонентами витрат, а `profit` — з доходом мінус витрати, якщо саме така формула передбачена бізнес-контрактом.
- **Рекомендовані дії:** перевірити формування `totalExpenses` на рівні садка та групи; уточнити, чи `expenses.meals` має входити до підсумку; додати unit/integration assertions на арифметичну узгодженість.
- **Примітка:** це не спростовує проходження E2E потоку платежу — дохід 25900 для групи 27 відобразився у звіті. Але розрахунок деталізації витрат має окрему невідповідність.

### Знайдені дефекти

**BUG-006: `DELETE /children/:id` для дитини з оплатами повертає 500 замість 409**

- **Очікувано:** 409 «Не можна видалити дитину, для якої збережена історія платежів».
- **Фактично:** 500. PostgreSQL повертає код `23001` (RESTRICT), Prisma не мапить його на `P2003`, тому обробка в `children.service.js` не спрацьовує.
- **Наслідок:** дані не пошкоджені, дитина лишається, але відповідь API хибна.
- **Виправлення:** явна перевірка кількості оплат перед видаленням (`children.service.js`, метод `remove`).
- **Виявлено:** автотест `children + payments: дитину з оплатами не можна видалити`.
- **Статус:** FIXED, перевірено тестом.

### Спостереження (не дефекти)

1. **Код відповіді для віку поза 2–5.** Було `409 Conflict`. За рішенням команди змінено на `400 Bad Request` (`assertChildAge`, `children.service.js`). `409` лишається для невідповідності віку дитини віку групи та для переповненої групи. Рішення команди: лишаємо як є.
2. **Рахунок завжди за поточними цінами й віком на сьогодні.** `periodStart` лише записується в знімок і на суму не впливає. Рішення команди: лишаємо як є.
3. **Дублі оплат.** Для однієї дитини й одного `periodStart` можна створити кілька платежів; обмеження унікальності немає. Допустимо за вимогами, рішення команди: лишаємо як є.
4. **Залежність від стану бази.** `tests/api.test.js` (`PUT /settings/prices приймає коректне оновлення`) пише в реальні ціни, тому суми в рахунках залежать від того, хто останній змінював ціни. У нових тестах ціни виставляються явно й повертаються в `after`. Рішення команди: лишаємо як є.

- **Причина:** у `schema.prisma` зв'язки `Child.group` і `Staff.group` необов'язкові, `onDelete` не вказано, тому Prisma обнуляє `group_id`, а обробка `P2003` в сервісі не спрацьовує.
- **Очікувано:** 409 «Не можна видалити групу, до якої прив'язані діти або персонал».
- **Наслідок:** діти й вихователі лишаються без групи, що ламає розклад і звіти.
- **Виправлення:** явна перевірка кількості дітей і персоналу перед видаленням (`groups.service.js`, `groups.repository.js`, метод `countStaff`). Схему й міграції не змінювали.
- **Статус:** FIXED, перевірено тестом.

**BUG-009: `DELETE /rooms/:id` без обробки помилки зовнішнього ключа**

- **Опис:** між перевіркою `_count.groups` і видаленням кімнату можна закріпити за групою, тоді відповідь була б 500.
- **Виправлення:** запасна обробка `P2003` → 409 (`rooms.service.js`, метод `delete`).
- **Статус:** FIXED (захисне виправлення, відтворити гонку вручну складно).

**BUG-010: Swagger не збігається з фактичними відповідями**

- `DELETE /groups/{id}` і `DELETE /rooms/{id}` описані як 204, код повертає 200.
- `POST /rooms` описував 409, якого створення кімнати не повертає.
- `POST /groups` і `PATCH /groups/{id}` не описували 404 для неіснуючої кімнати.
- **Виправлення:** `groups.docs.js`, `rooms.docs.js`.
- **Статус:** FIXED.

**BUG-011: відсутній унікальний індекс на `groups.room_id`**

- **Опис:** правило «одна кімната — одна група» перевіряється лише в сервісі (`validateRoom`). Два одночасні запити з одним `roomId` теоретично можуть обидва пройти.
- **Рекомендація:** часткова унікальна SQL-міграція `CREATE UNIQUE INDEX ... ON groups (room_id) WHERE room_id IS NOT NULL` і обробка `P2002`.
- **Статус:** OPEN, не виправлялось перед здачею, бо потребує міграції; у звичайному використанні малоймовірно.

**BUG-012: `PATCH /groups/:id` і `PATCH /rooms/:id` з порожнім тілом повертають 200**

- **Очікувано:** 400 (для `PUT /settings/prices` це вже виправлено, BUG-004).
- **Фактично:** 200, нічого не змінюється.
- **Вплив:** низький, правила не порушуються.
- **Статус:** OPEN.

**BUG-013: у `prisma/seed.js` різні формати даних дитини**

- **Опис:** основний сценарій використовує `fullName`, `parents`, `relative`, `benefit: "LEVEL_1"`, а демо-історія змін використовує `name`, `guardians`, `relativeVip`, `benefitType: "none"/"medium"`.
- **Ризик:** один із форматів може не відповідати схемі API дітей, що вплине на інвойс і звіти.
- **Рекомендація:** звірити з `children.schema.js` і привести до одного формату; це модуль дітей.
- **Статус:** OPEN, передано відповідальному за модуль дітей.

### Спостереження (не дефекти)

1. **Коди відповідей у групах і кімнатах.** Вік групи поза 2–5 дає `400` (валідація zod). `409` лишається для бізнес-правил: ліміт, вік дітей, зайнята кімната, видалення групи чи кімнати. Це узгоджено з рішенням щодо дітей (BUG-006, спостереження 1).
2. **Права.** Групи: читання, запис і видалення для Admin і Manager. Кімнати: читання для Admin і Manager, запис і видалення лише для Admin (`access.js`).
3. **Ідентифікатори після seed.** `TRUNCATE ... RESTART IDENTITY` у seed застосовується лише до `history`, тому `id` кімнат і груп після повторного запуску не починаються з 1. Тести не повинні покладатися на жорсткі id. Рішення: лишаємо як є.
