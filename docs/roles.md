# Права ролей

Документ описує розподіл прав доступу між ролями Admin, Manager, Parent і Teacher відповідно до вимог README та прийнятих командою рішень.

Для доступу до захищених ендпоінтів користувач повинен пройти авторизацію. Перевірка ролей і належності даних користувачу реалізована не для всіх ендпоінтів. Тому в документі окремо наведено цільовий розподіл прав і фактичний стан їх реалізації.

**Джерела:** README, розділи 3 і 6; реалізація маршрутів, middleware, контролерів і сервісів відповідних модулів.

## 3. Прийняті припущення та цільові правила доступу

1. Parent має доступ лише до інформації про власних дітей.
2. Parent може переглядати рахунки та платежі лише власних дітей.
3. Parent може переглядати заняття та розклад лише групи, до якої належить його дитина.
4. Parent може оновлювати додаткову інформацію про власну дитину відповідно до FR-04.
5. Parent не може створювати або видаляти записи дітей відповідно до FR-05.
6. Teacher має доступ лише до власного розкладу та занять у межах своєї відповідальності.
7. Teacher не має доступу до фінансових звітів, управління персоналом, групами та історією змін.
8. Manager має доступ до операцій, передбачених його роллю, але не має адміністративних прав Admin.
9. Admin має доступ до адміністративних функцій системи, зокрема управління персоналом, предметами, розкладом, цінами, звітами та історією змін.
10. Доступ Parent до даних дитини повинен визначатися за зв'язком між обліковим записом користувача та записом дитини.
11. Доступ Teacher до власних занять і розкладу повинен визначатися за зв'язком між обліковим записом користувача та записом працівника.
12. Прогнозування прибутку та прогнозування розкладу є адміністративними функціями й у цільовому розподілі прав доступні лише Admin.

## 5. Загальні правила доступу

1. Користувач повинен пройти авторизацію перед отриманням доступу до захищених ендпоінтів.
2. Після авторизації система повинна перевіряти роль користувача та відповідність запитуваної операції його правам.
3. Parent повинен отримувати доступ лише до даних власних дітей. Для цього необхідно перевіряти зв'язок між обліковим записом батьків і дитиною.
4. Teacher повинен переглядати власний розклад і працювати із заняттями лише в межах своєї відповідальності.
5. Admin повинен мати доступ до адміністративних функцій системи.
6. Якщо роль користувача не має права на виконання операції, система повинна відхилити запит.
7. Відсутність перевірки ролі або належності даних користувачу не повинна вважатися дозволом на доступ відповідно до цільових правил.

## 6. Примітки

- Матриця в розділі 1 описує цільовий розподіл прав доступу між ролями користувачів.
- Додаткові права для модулів Pricing і Rooms наведені як командні припущення.
- JWT-авторизація реалізована: користувач входить через `POST /auth/login`, після чого для доступу до захищених ендпоінтів використовується токен.
- У `src/app.js` middleware `authenticate` підключається перед маршрутами основних модулів.
- Маршрути `/health`, `/openapi.json`, `/docs` та `/auth` підключені до глобального middleware авторизації окремо.
- Глобальна JWT-авторизація не означає, що для кожного ендпоінта реалізована перевірка ролі або належності даних користувачу.
- Перевірка ролей реалізована лише на окремих маршрутах. Зокрема, `GET /reports/forecast-profit` доступний лише Admin, а маршрути модуля `/users` обмежені роллю Admin.
- Для багатьох інших перевірених модулів обмеження за ролями та належністю даних користувачу ще не реалізовані.
- Якщо `AUTH_ENABLED=false`, middleware авторизації пропускає перевірки, тому рольові обмеження не застосовуються.
- Фактичний стан реалізації наведено за перевіреним кодом і він може змінюватися після внесення змін до відповідних модулів.
- Повноту переліку ендпоінтів необхідно звіряти з актуальним README та файлами маршрутів проєкту.
