# Права ролей

Документ описує цільовий і фактичний розподіл прав доступу між ролями Admin, Manager, Parent і Teacher відповідно до вимог README та прийнятих командою рішень.

Для доступу до захищених ендпоінтів користувач повинен пройти JWT-авторизацію. Після успішної авторизації система отримує ідентифікатор користувача та його роль. Перевірка ролей і належності даних користувачу виконується окремо на рівні маршрутів.

У документі окремо наведено цільовий розподіл прав і фактичний стан їх реалізації.

**Джерела:** README, розділи 3 і 6; Swagger/OpenAPI; реалізація маршрутів, middleware, контролерів і сервісів відповідних модулів.

## 3. Прийняті припущення та цільові правила доступу

1. Parent має доступ лише до інформації про власних дітей.
2. Parent може переглядати рахунки та платежі лише власних дітей.
3. Parent може переглядати заняття та розклад лише групи, до якої належить його дитина.
4. Parent може оновлювати додаткову інформацію про власну дитину відповідно до FR-04.
5. Parent не може створювати або видаляти записи дітей відповідно до FR-05.
6. Teacher має доступ лише до власного розкладу та занять у межах своєї відповідальності.
7. Teacher не має доступу до фінансових звітів, управління персоналом, групами та історією змін.
8. Manager має доступ до дітей, груп, оплат і кімнат, але не має доступу до звітів, прогнозів, цін, персоналу та історії змін.
9. Admin має доступ до адміністративних функцій системи, зокрема управління персоналом, предметами, розкладом, цінами, звітами та історією змін.
10. Доступ Parent до даних дитини визначається за зв'язком між обліковим записом користувача та записом дитини.
11. Доступ Teacher до власних занять і розкладу визначається за зв'язком між обліковим записом користувача та записом працівника.
12. Прогнозування прибутку є адміністративною функцією та доступне лише Admin.
13. Доступ до захищених ендпоінтів здійснюється за допомогою JWT Bearer Token.
14. Якщо користувач не має необхідних прав для виконання операції, система повертає HTTP 403.

## 4. Фактичний стан реалізації прав доступу

Після реалізації рольового контролю доступу в PR #63 перевірка прав виконується на рівні маршрутів за допомогою конфігурації доступу та middleware `authorize`.

### 4.1. JWT-авторизація

| Елемент                       | Фактичний стан                                                             |
| ----------------------------- | -------------------------------------------------------------------------- |
| `POST /auth/login`            | Публічний маршрут авторизації. Приймає `login` і `password`.               |
| `authenticate`                | Перевіряє JWT для захищених маршрутів.                                     |
| `req.user`                    | Після успішної авторизації містить ідентифікатор користувача та його роль. |
| Відсутній або недійсний токен | Запит відхиляється з HTTP 401 за увімкненої авторизації.                   |
| Недостатньо прав за роллю     | Middleware `authorize` відхиляє запит з HTTP 403.                          |
| `AUTH_ENABLED=false`          | Перевірки авторизації через відповідне middleware обходяться.              |

### 4.2. Перевірка доступу за ролями

| Модуль / ендпоінти        | Фактичний стан                                                                                                                                  |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `/users`                  | Доступ лише для Admin.                                                                                                                          |
| `/reports/*`              | Усі маршрути звітів доступні лише для Admin.                                                                                                    |
| `/schedules/forecast`     | Доступ лише для Admin.                                                                                                                          |
| `/settings/prices`        | Доступ лише для Admin.                                                                                                                          |
| `/staff`                  | Доступ лише для Admin.                                                                                                                          |
| `/subjects`               | Доступ лише для Admin.                                                                                                                          |
| `/history`                | Доступ лише для Admin.                                                                                                                          |
| `/children`               | Admin і Manager мають доступ до операцій із дітьми; Parent — лише до власних дітей відповідно до перевірки належності.                          |
| `/groups`                 | Доступ для Admin і Manager.                                                                                                                     |
| `/payments`               | Admin і Manager мають доступ до операцій з оплатами; Parent — лише до платежів власних дітей.                                                   |
| `/rooms`                  | Admin і Manager мають доступ відповідно до дозволених для їхніх ролей операцій.                                                                 |

| `/schedules`              | Доступ лише для Admin.                                                                                                                          |
| `/children/:id/history`   | Доступ лише для Admin.                                                                                                                          |
| `/groups/:id/history`     | Доступ лише для Admin.                                                                                                                          |

### 4.3. Перевірка належності даних користувачу

- **Parent:** доступ до власних дітей визначається через зв'язок користувача з дитиною за допомогою `parent_id`.
- **Teacher:** зв'язок облікового запису користувача зі співробітником визначається через `staff.user_id`.
- **Розклад Teacher:** викладач може переглядати лише власний розклад. Спроба отримати розклад іншого викладача відхиляється з HTTP 403.
- **Заняття Teacher:** викладач може змінювати лише заняття, пов'язані з його обліковим записом через запис співробітника. Спроба змінити заняття іншого викладача відхиляється з HTTP 403.

### 4.4. Конфігурація доступу та тестування

- Розподіл прав між ролями централізовано визначається в `src/config/access.js`.
- Middleware `authorize` використовує налаштовані правила доступу для перевірки дозволів на маршрутах.
- Перевірка доступу виконується після JWT-авторизації.
- Для ролей, яким заборонено виконання операції, повертається HTTP 403.
- У `prisma/seed.js` передбачено зв'язування користувачів із відповідними записами: Parent — через `parent_id`, Teacher — через `user_id`.
- Перевірка роботи авторизації та рольових обмежень виконується тестами з `AUTH_ENABLED=true`.

## 5. Загальні правила доступу

1. Користувач повинен пройти авторизацію перед отриманням доступу до захищених ендпоінтів.
2. Після авторизації система перевіряє роль користувача та відповідність запитуваної операції його правам.
3. Parent отримує доступ лише до даних власних дітей. Для цього перевіряється зв'язок між обліковим записом батьків і дитиною.
4. Teacher переглядає власний розклад і працює із заняттями лише в межах своєї відповідальності.
5. Manager має доступ до дітей, груп, оплат і кімнат, але не до звітів, прогнозів, цін, персоналу та історії.
6. Admin має доступ до адміністративних функцій системи.
7. Якщо роль користувача не має права на виконання операції, система повертає HTTP 403.
8. Якщо користувач не пройшов JWT-авторизацію або токен недійсний, система повертає HTTP 401.
9. JWT-авторизація та перевірка ролей є різними рівнями контролю доступу.
10. Перевірка належності даних користувачу є обов'язковою для операцій, обмежених власними даними Parent і Teacher.

## 6. Примітки

- Матриця в розділі 1 описує цільовий розподіл прав доступу між ролями користувачів.
- Додаткові права для модулів Pricing і Rooms наведені як командні рішення.
- JWT-авторизація реалізована: користувач входить через `POST /auth/login`, передаючи `login` і `password`.
- Після успішного входу клієнт використовує отриманий токен у заголовку `Authorization: Bearer <token>`.
- У `src/app.js` middleware `authenticate` підключається перед маршрутами основних модулів.
- Маршрути `/health`, `/openapi.json`, `/docs` та `/auth` доступні без глобальної JWT-авторизації.
- Перевірка ролей виконується окремим middleware `authorize` на маршрутах відповідно до конфігурації `src/config/access.js`.
- Правила доступу застосовуються до маршрутів згідно з матрицею ролей.
- Якщо `AUTH_ENABLED=false`, перевірки через middleware авторизації обходяться. Для перевірки рольових обмежень необхідно використовувати `AUTH_ENABLED=true`.
- Фактичний стан реалізації враховує зміни PR #63.
- У разі зміни маршрутів, middleware або правил доступу цей документ необхідно синхронізувати з актуальними файлами реалізації та Swagger/OpenAPI.
