# Test Cases — Kindergarten API

## 1. Загальна інформація

**Проєкт:** Kindergarten API  
**Тип тестування:** автоматизоване та ручне тестування API  
**Інструменти:** Node.js Test Runner (`node:test`), Postman  
**Дата актуалізації:** 02.11.2026  
**Останній відомий повний запуск:** `npm.cmd test`  
**Результат:** 113 тестів: 112 PASS, 1 FAIL; тривалість приблизно 6,22 с.  
**Середовище БД:** використання саме тестової БД із `.env` під час останнього запуску окремо не підтверджено.

### Статуси

- **PASS** — перевірку виконано, фактичний результат відповідає очікуваному.
- **FAIL** — перевірку виконано, фактичний результат не відповідає очікуваному.
- **NOT RUN** — перевірку не виконували або немає підтвердженого результату.
- **BLOCKED** — перевірку неможливо виконати через відсутність необхідної реалізації чи залежності.
- **REVIEW** — відповідь отримано, але правильність поведінки треба звірити з контрактом або бізнес-правилами.

Статус HTTP-запиту та статус перевірки бізнес-логіки фіксуються окремо. Успішний HTTP 200 сам по собі не доводить правильність розрахунків.

## 11. Звіти — Reports

### TC-RE-001 — Отримання звіту про прибуток за місяць
- **Метод / endpoint:** `GET /reports/profit?month=2026-11`
- **Очікувано:** HTTP 200 та звіт за вказаний місяць.
- **Фактично:** отримано звіт за `2026-11`; дохід `25900`, tuition `16000`, meals `9900`, витрати `1200000`, прибуток `-1174100`.
- **Статус:** PASS для доступності endpoint і повернення звіту.

### TC-RE-002 — Отримання звіту про мінімальну кількість кімнат
- **Метод / endpoint:** `GET /reports/min-rooms`
- **Очікувано:** HTTP 200 та JSON.
- **Фактично:** HTTP/JSON перевірка проходила; окрема автоматизована перевірка розрахунку завершилася невдало.
- **Статус:** PASS лише для доступності endpoint / JSON; не означає правильність розрахунку.

### TC-RE-003 — Перевірка арифметики звіту про прибуток
- **Метод / endpoint:** `GET /reports/profit?month=2026-11`
- **Перевірка:** зіставити `expenses` із `totalExpenses`, а `revenue - totalExpenses` із `profit`.
- **Фактично:** на загальному рівні `25900 - 1200000 = -1174100`, тобто `profit` узгоджується з повернутим `totalExpenses`. Але сума компонентів витрат `200000 + 1000000 + 0 + 9900 = 1209900`, що на 9900 більше за `totalExpenses`. Для групи 27 `expenses.meals=9900`, але `totalExpenses=0` і `profit=25900`.
- **Статус:** FAIL — невідповідність між деталізацією витрат і підсумком. Див. BUG-005.

### TC-RE-004 — Перевірка розрахунку мінімальної кількості кімнат
- **Метод / endpoint:** `GET /reports/min-rooms`
- **Очікувано в автоматизованому тесті:** `data.rooms === 8` та `data.margin === 91000`.
- **Фактично:** `data.rooms = 7`; assertion зупинив тест до перевірки `margin`.
- **Статус:** FAIL. Не робити висновок про фактичне значення `margin`, оскільки assertion не був досягнутий.

## 15. Підсумок автоматизованого тестування

**Останній повний запуск:** `npm.cmd test`  
**Дата:** 02.11.2026  
**Результат:** 113 тестів загалом; 112 PASS; 1 FAIL; приблизно 6,22 секунди.

Єдиний відомий failure:
- `tests/reports.api.test.js` — `GET /reports/min-rooms повертає мінімальну кількість кімнат`.
- Очікувалося `data.rooms = 8`, фактично `data.rooms = 7`.
- Перевірка `data.margin === 91000` не була виконана через попередній assertion failure.

Окремий попередній API-only запуск: 22/22 PASS (приблизно 7,09 секунди); після останніх змін його повторний запуск не підтверджено. Не підміняти цим результатом повний `npm test`.

### Висновок

**Загальний результат повного автоматизованого запуску: FAIL** через одну невдалу перевірку `GET /reports/min-rooms`. E2E у Postman пройшов, але у звіті про прибуток виявлено окрему арифметичну невідповідність. Перш ніж закривати QA, потрібно розібрати BUG-003 і BUG-005, повторити повний `npm test` на підтвердженій тестовій БД із `.env`, а також виконати неперевірені сценарії модуля занять.

## 16. Історія змін (FR-34–FR-36, T2–T4)

### TC-HIST-001 — Фіксація операції створення (create)
- **Метод / сценарій:** створення сутності (наприклад, `POST /children`)
- **Очікувано:** у таблиці `history` створюється запис: `action = "create"`, `changes.before = null`, `changes.after` містить повний знімок створеного об'єкта, `createdAt` в ISO, заповнені `requestId` та `source = "api"`.
- **Статус:** PASS (покрито в `tests/history.core.test.js` та `tests/history.models.test.js`).

### TC-HIST-002 — Фіксація операції оновлення (update)
- **Метод / сценарій:** зміна існуючого запису (наприклад, `PATCH /children/:id`)
- **Очікувано:** у таблиці `history` з'являється новий запис: `action = "update"`, `changes.before` містить стан до зміни, `changes.after` — стан після зміни, `changedFields` містить масив назв змінених полів.
- **Статус:** PASS (покрито в `tests/history.core.test.js`).

### TC-HIST-003 — Фіксація операції видалення (delete)
- **Метод / сценарій:** видалення запису (наприклад, `DELETE /children/:id`)
- **Очікувано:** у таблиці `history` з'являється запис: `action = "delete"`, `changes.before` містить повний стан запису перед видаленням, `changes.after = null`. Сам запис історії зберігається навіть після видалення сутності (незмінність за FR-35).
- **Статус:** PASS (покрито в `tests/history.core.test.js`).

### TC-HIST-004 — Масові операції (createMany / deleteMany)
- **Метод / сценарій:** групові зміни даних у базі через один запит
- **Очікувано:** для кожного зачепленого рядка створюється окремий запис історії із спільним `requestId`.
- **Статус:** REVIEW / BLOCKED (очікує перевірки сумісності розширення Prisma або міграції на тестовій БД).

### TC-HIST-005 — Маскування конфіденційних полів (FR-36)
- **Метод / сценарій:** збереження або зміна сутностей, що містять чутливі дані (`passwordHash`, `password`, `token`)
- **Очікувано:** у знімках `changes.before` та `changes.after` значення цих полів замінені на `"***"`.
- **Статус:** PASS (перевірено автотестом `tests/history.models.test.js`).

### TC-HIST-006 — Отримання списку історії з фільтрами (GET /history)
- **Метод / endpoint:** `GET /history?entity=child&entityId=1&action=create`
- **Очікувано:** HTTP 200, повертається масив записів, відфільтрованих за параметрами, сортування від найновіших до найстаріших (`createdAt DESC`). При невалідних параметрах фільтрації — HTTP 400.
- **Статус:** PASS (покрито в `tests/history.api.test.js`).

### TC-HIST-007 — Отримання стану запису на момент часу (GET /history/state)
- **Метод / endpoint:** `GET /history/state?entity=child&entityId=1&at=<ISO_DATE>`
- **Очікувано:** повертається точний знімок стану сутності на зазначений момент часу `at`. Якщо на цей момент запису ще не існувало або його вже було видалено — HTTP 404.
- **Статус:** PASS (покрито в `tests/history.state.test.js`).

### TC-HIST-008 — Незмінність історії (відсутність PATCH і DELETE)
- **Метод / endpoint:** `PATCH /history/:id`, `DELETE /history/:id`
- **Очікувано:** HTTP 404 (або 405 Method Not Allowed), мутація чи видалення записів аудиту через API неможливі (FR-35).
- **Статус:** PASS (маршрути модифікації відсутні у модулі `history`).

### TC-HIST-009 — Обмеження «SQL, але все в JSON» (T2–T4)
- **Метод / сценарій:** перевірка схеми моделі `HistoryEntry`
- **Очікувано:** таблиця `history` містить виключно колонки `id` (PK) та `data` (`Json`). Усі метадані аудиту зберігаються виключно всередині JSON-об'єкта. Спроба зберегти запис без обов'язкових полів відхиляється валідацією.
- **Статус:** PASS (перевірено автотестом `tests/history.models.test.js`).
