# Сценарій історії змін: дитина

Контрольний сценарій для перевірки FR-34–FR-36. За ним тестують історію Марта, Аліна, Денис і Назар.

## Підготовка

- Сервер запущено, база наповнена: `npm run seed`.
- Є дві групи одного віку (FR-07): група A і група B, у кожній менше 20 дітей. Одна кімната обслуговує одну групу, тому для групи B спочатку створіть кімнату (`POST /rooms`), потім групу (`POST /groups`).
- Дата народження така, щоб дитині було 3 роки на день перевірки (FR-01). Приклад: `2023-05-10`.

## Кроки

| Крок | Запит                   | Тіло запиту                                                                                                                     |
| ---- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `POST /children`        | `{ "name": "Тест Дитина", "birthDate": "2023-05-10", "guardians": ["Мати Тест"], "benefitType": "none", "groupId": <група A> }` |
| 2    | `PATCH /children/{id}`  | `{ "groupId": <група B> }`                                                                                                      |
| 3    | `PATCH /children/{id}`  | `{ "benefitType": "medium" }` (пільга 20%)                                                                                      |
| 4    | `DELETE /children/{id}` | немає                                                                                                                           |

## Очікувані записи історії

У кожного запису: `entity` = `children`, `entityId` = `{id}`, `actor` = `null` (поки немає авторизації), `source` = `api`, `changedAt` зростає від кроку до кроку.

| Крок | action | changedFields | before                                                          | after                                               |
| ---- | ------ | ------------- | --------------------------------------------------------------- | --------------------------------------------------- |
| 1    | create | —             | `null`                                                          | повний запис: `groupId` = A, `benefitType` = `none` |
| 2    | update | `groupId`     | `groupId` = A                                                   | `groupId` = B, решта полів без змін                 |
| 3    | update | `benefitType` | `benefitType` = `none`                                          | `benefitType` = `medium`, решта полів без змін      |
| 4    | delete | —             | остання версія запису (`groupId` = B, `benefitType` = `medium`) | `null`                                              |

Правило: `before` кожного кроку дорівнює `after` попереднього.

## Перевірки

1. `GET /history?entity=children&entityId={id}` повертає 4 записи, нові першими: delete, update (пільга), update (група), create.
2. `GET /history/{id}` для кожного з чотирьох записів повертає той самий запис, що в списку.
3. `GET /history/state?entity=children&entityId={id}&at=<час між кроками 2 і 3>`: `groupId` = B, `benefitType` = `none`.
4. `GET /history/state` з часом між кроками 3 і 4: `groupId` = B, `benefitType` = `medium`.
5. `GET /history/state` з часом до кроку 1 або після кроку 4: 404.
6. `GET /children/{id}/history` до кроку 4 повертає записи кроків 1–3; після видалення дитини цей маршрут повертає 404, тож історію видаленої дитини беремо через `GET /history`.
7. `PATCH` і `DELETE` для `/history` не існують (404).

## Критерій успіху

Усі чотири записи є, поля збігаються з таблицею, історія не змінюється після видалення дитини.

## Примітка

Назви полів (`groupId`, `benefitType`) взято зі схеми валідації дітей. Якщо в коді вони інші, замініть їх у файлі й повідомте Марту.
