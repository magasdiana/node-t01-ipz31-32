# Handover: запуск проєкту Kindergarten API

Backend для системи управління приватним дитячим садком.

**Технології:** Node.js, Express 5, Prisma ORM, PostgreSQL (Neon).

Проєкт реалізований як REST API без frontend-частини. Основні дані зберігаються у JSON-колонках `data`, а таблиці містять первинні та зовнішні ключі. Історія змін доступна через окремі API-ендпоінти.

---

## 1. Вимоги

Для запуску проєкту потрібні:

- Node.js `v22.13`
- npm `10.9.2`
- Git
- База даних PostgreSQL у Neon або інший доступний PostgreSQL-сервер

Neon — хмарний PostgreSQL-сервіс, локально його встановлювати не потрібно.

## 2. Запуск проєкту з нуля

### Крок 1. Клонування репозиторію

```bash
git clone <repo-url>
cd node-t01-ipz31-32
```

### Крок 2. Встановлення залежностей

```bash
npm install
```

### Крок 3. Налаштування змінних середовища

Створіть файл `.env` на основі `.env.example`.

У Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

В інших терміналах:

```bash
cp .env.example .env
```

Відкрийте `.env` і вкажіть у `DATABASE_URL` рядок підключення до вашої бази PostgreSQL. Для Neon використовуйте рядок підключення з панелі Neon із параметром `?sslmode=require`.

Інші змінні для локального запуску можна залишити за замовчуванням. Детальніше — у розділі 3.

### Крок 4. Застосування міграцій

```bash
npx prisma migrate deploy
```

Команда застосовує наявні міграції до бази даних.

### Крок 5. Генерація Prisma Client

```bash
npx prisma generate
```

### Крок 6. Заповнення бази даних

```bash
npm run seed
```

Seed створює початкові дані та демоакаунти для роботи й тестування API.

**Увага:** повторний запуск `npm run seed` очищує наявні дані перед повторним заповненням. Не запускайте цю команду на базі з даними, які потрібно зберегти.

Команда `npx prisma migrate reset` також очищує базу та автоматично запускає seed. Не використовуйте її на базі з важливими даними.

Seed заборонений у production (`NODE_ENV=production`).

### Крок 7. Запуск сервера

Звичайний запуск:

```bash
npm start
```

Для розробки з автоматичним перезапуском:

```bash
npm run dev
```

Без `JWT_SECRET` у `.env` сервер не запуститься, оскільки перевірка секретного ключа виконується під час запуску.

## 3. Змінні середовища

Шаблон `.env.example` у корені проєкту:

```dotenv
# Підключення до PostgreSQL
DATABASE_URL="postgresql://user:password@localhost:5432/garden?schema=public"

PORT=3000
NODE_ENV=development

JWT_SECRET=local_test_secret_key_2026
# Термін дії токена (формат jsonwebtoken: 15m, 8h, 7d)
JWT_EXPIRES_IN=8h
# true за замовчуванням. false працює лише поза production (для тестів без токена).
# У production (NODE_ENV=production) авторизація завжди увімкнена.
AUTH_ENABLED=true
```

| Змінна           | Призначення                                                                                          |
| ---------------- | ---------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`   | Рядок підключення до PostgreSQL. Для Neon візьміть його в панелі Neon у розділі підключення до бази. |
| `PORT`           | Порт сервера. Якщо не вказаний, використовується `3000`.                                             |
| `NODE_ENV`       | Середовище запуску (`development`, `production`).                                                    |
| `JWT_SECRET`     | Секретний ключ для підпису JWT. Обов'язковий: без нього сервер не запуститься.                       |
| `JWT_EXPIRES_IN` | Термін дії токена у форматі `jsonwebtoken` (`15m`, `8h`, `7d`). У шаблоні — `8h`.                    |
| `AUTH_ENABLED`   | Перемикач авторизації. За замовчуванням `true`; `false` працює лише поза production.                 |

У production (`NODE_ENV=production`) авторизація завжди увімкнена незалежно від `AUTH_ENABLED`.

Значення `JWT_SECRET` у `.env.example` призначене лише для локальної розробки та тестування. Для production потрібно використовувати власний надійний секретний ключ.

Файл `.env` містить конфіденційні дані, тому його не додають до Git. Для налаштування середовища використовуйте `.env.example` як шаблон.

## 5. Демо-акаунти та ролі

Користувачі створюються seed-скриптами:

- `prisma/seed.users.js` — створення користувачів та їхніх облікових даних;
- `prisma/seed.js` — заповнення бази та зв'язування користувачів із сутностями (parent — з дитиною, teacher — зі співробітником).

Після `npm run seed` доступні такі демоакаунти:

| Роль    | Логін     | Пароль         | Призначення            | Доступ                                                    |
| ------- | --------- | -------------- | ---------------------- | --------------------------------------------------------- |
| Admin   | `admin`   | `Admin#2026`   | Адміністратор          | Повний доступ до дозволених адміністративних операцій     |
| Manager | `manager` | `Manager#2026` | Менеджер               | Робота з дітьми, групами, оплатами та кімнатами           |
| Parent  | `parent`  | `Parent#2026`  | Батько або мати дитини | Перегляд інформації лише про свою дитину та власні оплати |
| Teacher | `teacher` | `Teacher#2026` | Викладач               | Перегляд власного розкладу та робота зі своїми заняттями  |

Паролі призначені лише для локальної розробки та демонстрації. Seed у production заборонений.

У базі паролі зберігаються як хеші bcryptjs, API їх не повертає.

Лише демо-користувачів (без решти даних) можна створити окремо:

```bash
node prisma/seed.users.js
```

Якщо логін уже існує, дублікат не створюється.

## 7. Forecast

У проєкті доступні два типи прогнозування:

- `GET /reports/forecast-profit` — прогноз прибутку;
- `GET /schedules/forecast` — прогноз розкладу.

Прогнози розраховуються на основі параметрів запиту та поточних даних, які використовуються як значення за замовчуванням. Вони не створюють реальні заняття та не записують результати прогнозування в таблиці `lessons` і `history`.

### Параметри прогнозування

| Параметр   | Опис                                                                                                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `groups`   | Кількість груп. Додатне ціле число. За замовчуванням — поточна кількість груп із бази даних.                                                                         |
| `children` | Загальна кількість дітей (ціле число ≥ 0) або розподіл дітей між групами через кому, наприклад `15,12,18`. За замовчуванням — поточна кількість дітей із бази даних. |
| `months`   | Період прогнозу в місяцях — ціле число від 1 до 12. Значення за замовчуванням — 3.                                                                                   |

Якщо `children` передано одним числом, воно визначає загальну кількість дітей.

Якщо `children` передано списком через кому, кожне число визначає кількість дітей в окремій групі. Кількість елементів списку повинна дорівнювати значенню `groups`.

Приклад розподілу:

```text
groups=3
children=15,12,18
```

У цьому випадку прогноз розраховується для трьох груп із 15, 12 та 18 дітьми відповідно.

### Прогноз прибутку

`GET /reports/forecast-profit` розраховує прогнозований прибуток на основі переданих параметрів, а не історичних фінансових записів із бази даних.

У результаті прогнозування також визначається точка плато відповідно до вимоги FR-32.

Окремий endpoint `/reports/optimum` для цього не створюється.

### Прогноз розкладу

`GET /schedules/forecast` формує прогнозований розклад на основі спрогнозованої кількості груп і дітей.

Результат повертається як чернетка розкладу без запису до бази даних.

Відповідь прогнозу містить:

- `lessons` — заняття, які вдалося запланувати;
- `unscheduled` — заняття, які не вдалося розмістити. Кожен елемент має `groupId`, `subjectId`, `reason`, `code` (`NO_TEACHER` або `NO_SLOT`) і для `NO_SLOT` — `blockedBy` (що блокувало: `teacher`, `group`, `room`, `daily_limit`);
- `conflicts` — виявлені конфлікти;
- `roomsNeeded` — кількість потрібних кімнат (по одній на групу);
- `teachersNeeded` — оцінка кількості потрібних викладачів: задіяні в чернетці плюс по одному на кожен гурток, який не вдалося закрити;
- `scenario` — сценарій, за яким побудовано прогноз: `groups` (`groupId`, `roomId`, `childrenCount`, `isVirtual`) і `totalChildren`. Віртуальні групи мають від'ємний `groupId` і `roomId = null`.

`POST /schedules` без поля `save` (або з `save: false`) повертає лише чернетку (200). Із `save: true` розклад зберігається (201), але лише якщо розставлено всі заняття; інакше 409 і нічого не записується. Перегенерація окремих груп (`groupIds`) планується навколо занять інших груп, що лишаються.

Прогноз дає змогу оцінити можливість формування розкладу для заданої кількості груп і дітей без створення реальних занять у системі.

## 8. Swagger і Postman

### Swagger UI

Після запуску сервера документація доступна за адресою:

`http://localhost:3000/docs/`

У Swagger можна:

- переглянути доступні API-операції;
- ознайомитися з параметрами запитів;
- переглянути структуру відповідей;
- перевірити вимоги до авторизації;
- виконати тестові запити до API.

OpenAPI-специфікація у форматі JSON доступна за адресою:

`http://localhost:3000/openapi.json`

Для перевірки захищених ендпоінтів спочатку виконайте `POST /auth/login`, отримайте JWT-токен і використайте його через кнопку **Authorize** у Swagger.

### Postman

Колекція запитів:

`docs/postman_collection.json`

Щоб імпортувати колекцію:

1. Відкрийте Postman.
2. Натисніть **Import**.
3. Виберіть файл `docs/postman_collection.json`.
4. Перевірте змінну `baseUrl` (`http://localhost:3000`).
5. Виконайте `POST /auth/login` і передайте отриманий JWT у заголовку `Authorization: Bearer <token>`.

Колекція містить запити для основних ресурсів, ролей, прогнозів, оплат, налаштувань цін та історії змін.

## 9. Відомі обмеження та особливості

- Авторизація у production завжди увімкнена; `AUTH_ENABLED` діє лише поза production.
- Перегляд історії змін доступний лише Admin.
- Manager не має доступу до розкладу груп, звітів, прогнозів, налаштувань цін і персоналу.
- Parent може лише переглядати власні оплати.
- Teacher працює лише зі своїми заняттями та переглядає власний розклад.
- Прогнози не створюють реальні заняття та не змінюють історію змін.
- Прогноз розкладу повертається як чернетка без запису до бази даних.
- Бізнес-припущення та константи зберігаються у `src/config/constants.js` і `docs/decisions.md`.
- Посада вихователя в системі називається `educator`.
- Контрольні фінансові значення: маржа групи — 91 000, постійні витрати — 680 000, мінімальна кількість груп — 8.
- Відкриті питання та відомі проблеми описані у `docs/bugs.md`.

## Швидкий старт після клонування

```bash
npm install
cp .env.example .env
```

Після створення `.env` вкажіть власний `DATABASE_URL` та перевірте `JWT_SECRET`.

Далі виконайте:

```bash
npx prisma migrate deploy
npx prisma generate
npm run seed
npm start
```

**Увага:** `npm run seed` очищує наявні дані перед заповненням. Використовуйте цю команду лише на новій або тестовій базі, дані якої можна видалити.
